## Change 1: Rainbow is Global — Four Palettes, CVD-Separated

Rainbow tokens are no longer generated by the theme engine. They become global static CSS files — one per vision type. Each palette is hand-picked for maximum distinguishability within that vision type's safe range.

**Why separate palettes:** There are almost no colours safe for ALL three CVD types simultaneously. What's safe for protan/deutan (blue-yellow axis) is dangerous for tritanopia, and vice versa. So each CVD type gets its own optimised palette.

### Four palettes:

| Palette | Who sees it | Axis | File |
|---|---|---|---|
| Default | Full vision | Full ROYGBIV | `rainbow-default.css` |
| Protan/Deutan | Red-green blind | Blue-yellow | `rainbow-protan.css` |
| Tritanopia | Blue-yellow blind | Red-green | `rainbow-tritan.css` |
| Monochrome | Greyscale users | Lightness only | `theme-chroma-mono.css` |

### Cascade order (later overrides earlier):

```
1. rainbow-default.css        → real ROYGBIV (always loaded)
2. rainbow-protan.css         → overrides if [data-cvd="protan"] or [data-cvd="deutan"]
3. rainbow-tritan.css         → overrides if [data-cvd="tritan"]
4. theme-chroma-mono.css      → overrides everything if [data-theme-chroma="grey"]
```

Monochrome wins over CVD — if user chose greyscale, they don't want colour at all.

### 5 tints per colour (35 tokens per palette):

| Tint | Lightness | Use case |
|---|---|---|
| `--rainbow-n-wash` | Very light (near page bg) | Page/section background fills |
| `--rainbow-n-light` | Light | Card tints, subtle highlights |
| `--rainbow-n` | Base | Confetti, scroll-draw, icons |
| `--rainbow-n-dark` | Dark | Patterns, borders, emphasis |
| `--rainbow-n-deep` | Very dark (near black) | Dark overlays, deep accents |

### Dark mode rainbow flip in `theme-luminance-dark.css`:

Dark mode swaps wash↔deep and light↔dark. Base stays. This applies to whichever palette is active:

```css
[data-theme-luminance="dark"] {
  /* Swap wash and deep */
  --rainbow-1-wash: var(--_r1-deep); --rainbow-1-deep: var(--_r1-wash);
  --rainbow-1-light: var(--_r1-dark); --rainbow-1-dark: var(--_r1-light);
  /* ... repeat for all 7 */
}
```

NOTE: The dark mode flip is tricky with var() because the values are already set. Simpler approach — each rainbow CSS file includes BOTH light and dark values:

```css
/* In rainbow-default.css */
:root {
  --rainbow-1-wash: #FDE8EA; --rainbow-1-deep: #3D0A0E; /* etc */
}
[data-theme-luminance="dark"] {
  --rainbow-1-wash: #3D0A0E; --rainbow-1-deep: #FDE8EA;
  --rainbow-1-light: #8B1A22; --rainbow-1-dark: #F0A0A8;
}
```

Each of the 3 rainbow files contains its own dark mode overrides. No separate dark flip file needed.

## Change 2: Remove CVD Logic from Engine

The engine no longer shifts colours for CVD safety. Safety lives in the picker UI — pre-tagged colour cards, "No Reds"/"No Blues" filters, pre-verified safe pairs.

### Remove from engine:

- Delete `applyDefinitionCVD()` entirely
- Delete `CVD_HUE_RULES` constant
- Delete `enforceHueSafety()` / `fixScaleCVD()`
- Delete `clampHueForCVD()`
- Delete `getCVDNeutralHue()` — neutral hue is now always warm (40°) or pure (0°), set by definition
- Delete all CVD-related parameters from function signatures
- Delete `cvd` field handling from `generateThemeData()`

### What stays:

- `safeOklch()` — gamut clamping is still needed (keeps colours in sRGB)
- Scale generation — unchanged, just no CVD pre-processing
- The `cvd` field in JSON definitions — used by the UI for filter metadata, NOT by the engine

### CVD variants in preset themes:

Previously: one base definition → engine shifts colours for CVD → generates variant.

Now: each CVD variant has its own explicit primary/secondary in the JSON:

```json
{
  "name": "warm-coral",
  "primary": "#f97066",
  "secondary": "#3b82f6",
  "variants": {
    "protan": { "primary": "#CC79A7", "secondary": "#0077BB" },
    "tritan": { "primary": "#f97066", "secondary": "#009988" }
  }
}
```

The build script reads the variants block and generates separate theme files with those explicit colours. No computation. Hand-picked safe pairs.

Protan and deutan share one variant (same safe colours for both). Total files per theme: 6 (default, dark, protan/deutan, protan/deutan-dark, tritan, tritan-dark).

No `getCVDNeutralHue()` function needed. The definition says what neutral to use.

## Change 5: Status Colours from Definition

Status colours respect the theme's chroma preset. No CVD-specific status hue tables in the engine — CVD variant definitions explicitly set their own status hues if needed.

### All status generation uses `safeOklch()` — no `chroma.hsl()`:

```js
const STATUS_HUES = { Success: 145, Warning: 45, Error: 15, Info: 215 };
```

### Status chroma respects theme character:

```js
const STATUS_CHROMA = {
  brand:  1.0,
  pastel: 0.45,
  neon:   1.4,
  grey:   0,
};
```

### CVD variant definitions can override status hues:

```json
{
  "name": "warm-coral-protan",
  "primary": "#CC79A7",
  "secondary": "#0077BB",
  "statusHues": { "Success": 220, "Warning": 85, "Error": 55, "Info": 280 }
}
```

If `statusHues` is present in the definition, the engine uses those. Otherwise it uses the defaults. The engine doesn't know or care why the hues are different — it just uses what the definition says.

## Change 6: High Contrast Brightening

HC themes must force primary and secondary to high lightness and maximum chroma BEFORE scale generation. The current brand sage (#8fa68a) is too muted for HC.

```js
if (definition.highContrast) {
  const priHue = chroma(definition.primary).oklch()[2];
  const secHue = chroma(definition.secondary).oklch()[2];
  definition.primary = safeOklch(0.80, 0.20, priHue);
  definition.secondary = safeOklch(0.75, 0.18, secHue);
}
```

### Order matters — CVD shift runs FIRST:

```
1. CVD shift (green → blue)
2. HC brighten (dim blue → vivid bright blue)
3. Generate scale from vivid shifted colour
```

### HC page backgrounds — pure white/black:

```css
/* HC dark */
--page-bg: #000000;
--page-bg-raised: #1a1a1a;
--page-bg-sunken: #000000;
--page-bg-overlay: #2c2c2c;

/* HC light */
--page-bg: #ffffff;
--page-bg-raised: #f5f5f5;
--page-bg-sunken: #eeeeee;
--page-bg-overlay: #fafafa;
```

HC is the ONLY theme that uses pure black and pure white.

## Change 7: Colour-Mono Theme Rules

When `primary === secondary` (colour-mono), secondary scale becomes greyscale:

```js
if (definition.primary === definition.secondary) {
  secondaryScale = generatePureGreyScale();
}
```

### Mono status — four lightness levels of the mono hue:

```js
if (isMonoPalette) {
  const hue = chroma(definition.primary).oklch()[2];
  status = {
    'color-Success': safeOklch(0.65, 0.06, hue),
    'color-Warning': safeOklch(0.55, 0.10, hue),
    'color-Error':   safeOklch(0.35, 0.14, hue),
    'color-Info':    safeOklch(0.45, 0.08, hue),
  };
}
```

### Mono CVD variants:

CVD variants of colour-mono are separate definitions with a different mono hue — e.g. red-mono's protan variant is purple-mono:

```json
{
  "name": "colour-mono",
  "primary": "#e63946",
  "secondary": "#e63946",
  "variants": {
    "protan": { "primary": "#AA44AA", "secondary": "#AA44AA" },
    "tritan": { "primary": "#e63946", "secondary": "#e63946" }
  }
}
```

No CVD logic in the engine. The definition says what colour. The engine builds from it.

## Change 8: Cream = Calm Theme

Cream is renamed to "Calm." It's a contrast strategy, not a colour choice. Compressed lightness range, low visual noise.

### Definition:

```json
{
  "name": "calm",
  "primary": "#a89279",
  "secondary": "#9bb5c4",
  "luminance": "light",
  "chroma": "pastel",
  "neutral": "warm"
}
```

### Calm has fixed zone hues — not derived from two browns:

```js
const CALM_ZONE_HUES = {
  primary:   40,    // warm beige
  secondary: 210,   // soft blue
  earth:     340,   // soft pink
  forest:    270,   // soft lilac
  dusk:      180,   // soft mint
  mist:      300,   // soft mauve
};
```

Use these when `chromaPreset === 'pastel'` instead of deriving from primary/secondary.

### Compressed lightness range:

```js
if (chromaPreset === 'pastel') {
  pageBgLightness = 0.92;    // not bright white
  bodyTextLightness = 0.38;  // not deep black
  // Contrast ~4.5:1 (AA floor, not AAA)
}
```

## Change 9: Remove Shadows from Theme Files

Shadow overrides live in `theme-luminance-dark.css`, NOT in theme files. Remove the entire shadows section from the engine output. The behavioural CSS layer handles it:

```css
[data-theme-luminance="dark"] {
  --shadow-xs: none;
  --shadow-sm: none;
  /* etc */
  --shadow-glow-primary: 0 0 14px color-mix(in oklch, var(--brand-c-primary) 50%, transparent);
}
```

## Do NOT

- Generate rainbow tokens in theme files — rainbow is global
- Compute CVD colour shifts in the engine — safety lives in the picker UI and JSON definitions
- Use `chroma.hsl()` for status colours — use `safeOklch()` only
- Output shadows in theme files — behavioural CSS handles it
- Duplicate protan and deutan files — one file, two selectors
- Use warm neutral (hue 40°) for protan/deutan variant definitions — use pure neutral
- Override agreed decisions without flagging — ask first
- Silently fix things — if unsure, flag it and ask
